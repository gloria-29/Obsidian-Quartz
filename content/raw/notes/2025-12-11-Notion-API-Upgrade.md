### **阅读笔记：Notion API 版本 2025-09-03 升级指南**

**来源：** Notion 官方文档 - 《Upgrading to Version 2025-09-03》  
**核心主题：** Notion API 引入对**多源数据库** 的首次全面支持，此次更新是一次**非向后兼容的重大变更**，要求所有现有的数据库集成进行迁移。

---

### **一、 全面摘要与核心观点**

本文档是 Notion API 一次里程碑式更新的官方迁移指南。核心变更在于引入了 **“数据源”** 这一新概念，将原有的“数据库”功能进行了分层：一个**数据库** 现在可以包含多个**数据源**。这解锁了更强大的工作流，但代价是 API 的重大重构。

**主要观点如下：**

1. **强制性升级：** 此次变更**非向后兼容**。如果集成不更新，当用户为数据库添加第二个数据源时，所有依赖该数据库的 API 操作都将失败。
2. **概念分离：** 原有的 &#96;database_id&#96; 在很多场景下被新的 &#96;data_source_id&#96; 所取代或补充。开发者需要理解数据库（容器）和数据源（内容）之间的关系。
3. **系统性迁移：** 升级不是一个简单的版本号切换，而是一个系统性的代码更新过程，涉及 API 端点、请求/响应结构、SDK 和 Webhook 等多个层面。
4. **分步指南：** 文档提供了清晰、详细的六步迁移检查清单，指导开发者安全、完整地完成升级。

---

### **二、 关键见解与重要细节**

#### **1. 变更的核心：从数据库到多源数据库**

- **旧模型：** 一个数据库对应一个固定的数据结构（属性/模式）。
- **新模型：** 一个数据库作为一个容器，可以包含多个数据源。每个数据源拥有自己独立的属性集合，但共享同一个数据库的视图、权限等设置。
- **影响：** 这使得在同一数据库视图下管理不同结构的数据成为可能（例如，一个“项目”数据库可以有一个用于“设计项目”的数据源和一个用于“开发项目”的数据源，两者属性不同）。

#### **2. 不兼容变更的具体表现**

如果集成未更新，以下操作在用户为数据库添加新数据源后会失败：

- 以数据库为父级创建页面
- 对数据库的读取、写入或查询操作
- 写入指向该数据库的关系属性

#### **3. 迁移检查清单（结构化分解）**

**步骤 1：发现并存储数据源 ID**

- **行动：** 在所有使用 &#96;database_id&#96; 的入口点，调用新的 &#96;GET /v1/databases/:database_id&#96; 端点（需设置 &#96;Notion-Version: 2025-09-03&#96;），以获取该数据库下的所有子数据源列表。
- **关键细节：** 一个数据库最初有一个默认数据源，但用户可能添加更多。集成必须能处理多个数据源 ID。

**步骤 2：在创建页面和关系中使用数据源 ID**

- **行动：**
  - **创建页面：** 将请求体中的 &#96;parent&#96; 从 &#96;{ &quot;database_id&quot;: &quot;...&quot; }&#96; 更改为 &#96;{ &quot;data_source_id&quot;: &quot;...&quot; }&#96;。
  - **关系属性：** 在写入关系属性时，请求体中只提供 &#96;data_source_id&#96;（而非 &#96;database_id&#96;）。
- **关键细节：** 此更改在升级 API 版本**之前**即可实施，因为它兼容旧版本 API，有助于平滑迁移。

**步骤 3：将数据库端点迁移至数据源端点**

- **行动：** 将大多数针对数据库内容的操作从 &#96;/v1/databases&#96; 命名空间迁移到 &#96;/v1/data_sources&#96; 命名空间，并使用数据源 ID。
- **受影响的 API 及变更细节：**
  - **检索：** &#96;GET /v1/databases/{id}&#96; 变为用于列出数据源。获取具体数据源的属性需使用新的 &#96;GET /v1/data_sources/{data_source_id}&#96;。
  - **查询：** &#96;POST /v1/databases/{id}/query&#96; 变为 &#96;POST /v1/data_sources/{data_source_id}/query&#96;。
  - **创建：** &#96;POST /v1/databases&#96; 仍用于创建数据库**及其初始数据源**，但初始数据源的属性现在放在 &#96;initial_data_source[properties]&#96; 字段下。为现有数据库添加新数据源需使用新的 &#96;POST /v1/data_sources&#96;。
  - **更新：** 职责分离。
    - **更新数据库** API：用于修改数据库容器本身的属性（如 &#96;title&#96;, &#96;parent&#96;, &#96;icon&#96;, &#96;cover&#96;, &#96;is_inline&#96;）。
    - **更新数据源** API：用于修改特定数据源的属性（即数据库模式 &#96;properties&#96;）。
- **关系属性响应：** 在所有 API 版本的**读取**操作中，关系属性响应现在都同时包含 &#96;database_id&#96; 和 &#96;data_source_id&#96;，以提供完整上下文。

**步骤 4：更新搜索 API 的处理逻辑**

- **行动：**
  - **请求：** 将搜索过滤条件中的 &#96;object&#96; 从 &#96;&quot;database&quot;&#96; 改为 &#96;&quot;data_source&quot;&#96;。
  - **响应处理：** 搜索结果现在返回的是 &#96;object: &quot;data_source&quot;&#96; 的对象。同一个数据库有多个数据源时，会返回多条结果。

**步骤 5：升级 TypeScript SDK 至 v5**

- **行动：** 在完成上述代码重构后，将 &#96;@notionhq/client&#96; 升级到 v5.0.0 或更高版本。
- **关键细节：** v5 SDK 提供了新的 &#96;notion.dataSources.*&#96; 和 &#96;notion.databases.*&#96; 方法，应替换迁移过程中使用的临时 &#96;notion.request(...)&#96; 调用。

**步骤 6：处理 Webhook 变更**

- **行动：**
  1. 在 Webhook 订阅设置中，将 API 版本升级到 &#96;2025-09-03&#96;。
  2. 确保你的 Webhook 处理器能够同时处理新旧格式的事件负载，进行充分测试后，再清理旧格式的支持代码。
- **关键变更：**
  - **新增事件类型：** &#96;data_source.created&#96;, &#96;data_source.moved&#96;, &#96;data_source.deleted&#96;, &#96;data_source.undeleted&#96;, &#96;data_source.schema_updated&#96;, &#96;data_source.content_updated&#96;。
  - **事件层级调整：** 原来与数据库内容/模式相关的事件现在下放至数据源级别。
  - **事件负载新增字段：** 所有以数据源为父级的事件（如 &#96;page.created&#96;）的 &#96;data.parent&#96; 对象中都会包含 &#96;data_source_id&#96; 字段，用于精确识别页面所属的数据源。

---

### **三、 重要结论与要点**

1. **必须行动：** 所有使用 Notion 数据库 API 的集成**都必须**参照此文档进行更新，否则将在用户使用多源数据库功能时出现服务中断。
2. **规划与测试：** 迁移过程涉及多处代码修改，不应被视为简单快捷的任务。建议制定迁移计划，并在测试环境中充分验证。
3. **概念理解是关键：** 成功迁移的前提是深刻理解**数据库**（作为容器和视图）与**数据源**（作为数据结构和内容的提供者）之间的新关系。
4. **利用官方资源：** 文档中提到的 [常见问题解答（FAQs）](/) 链接是重要的补充信息源，应在迁移前查阅。
5. **Webhook 需谨慎处理：** Webhook 的升级需要保证系统在过渡期间能处理两种事件格式，避免事件丢失或处理错误。

综上所述，Notion API 版本 &#96;2025-09-03&#96; 的升级是一次功能强大但要求严格的更新。通过遵循官方提供的结构化清单，开发者可以系统性地完成迁移，从而利用多源数据库带来的新潜力，同时确保集成的稳定性和未来兼容性。
