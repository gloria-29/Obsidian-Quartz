# 知识库构建方法论

> LLM Wiki 模式——让 AI 自动构建和维护个人知识库。由 Karpathy 推广的"LLM-as-compiler"理念，将知识管理从手动整理转变为 AI 驱动的持续合成。

## 核心概念

[[LLM Wiki]] 模式的核心洞察是：**知识应该是编译的，而非每次重新推导**。传统 RAG 在每次查询时从原始文档重新发现知识，而 LLM Wiki 由 LLM **增量构建并持续维护一个结构化的 Markdown Wiki**——一个存在于你和原始资料之间的、相互链接的持久知识体。

类比：Obsidian 是 IDE，LLM 是程序员，Wiki 是代码库。

## 主要内容

### 三层架构

LLM Wiki 由三个层次构成：

1. **Raw Sources（原始素材层）**：用户精选的源文件——文章、论文、图片、数据文件。不可变，LLM 只读不写。这是你的"事实来源"。
2. **The Wiki（Wiki 层）**：LLM 生成的 Markdown 文件目录——摘要、实体页、概念页、对比分析、总览、综合。LLM 完全拥有此层，负责创建、更新、维护交叉引用。
3. **The Schema（Schema 层）**：配置文件（如 CLAUDE.md 或 AGENTS.md），告诉 LLM Wiki 的结构、约定和流程。这是让 LLM 成为"守纪律的 Wiki 管理员"的关键。

### 核心工作流

- **Ingest（摄入）**：投入新源文件 → LLM 阅读、讨论要点 → 写摘要页 → 更新索引 → 更新相关实体和概念页 → 追加日志条目。一则源文件可能触及 10-15 个 Wiki 页面。
- **Query（查询）**：用户提问 → LLM 搜索相关页面 → 阅读并综合答案（含引用）。好答案可归档回 Wiki 作为新页面。
- **Lint（巡检）**：定期让 LLM 做 Wiki 健康检查——矛盾声明、过时主张、孤立页面、缺失交叉引用、数据空白。

### 索引与日志

- **index.md**：按内容分类的 Wiki 目录，每页列有链接、一行摘要和可选元数据
- **log.md**：按时间顺序的只追加记录（摄入、查询、巡检），每行以一致前缀开头方便 Unix 工具解析

### 与传统 RAG 的区别

| 维度 | 传统 RAG | LLM Wiki |
|------|----------|----------|
| 知识存储 | 查询时临时检索 | 持久编译的 Wiki |
| 跨文档综合 | 每次重做 | 持续累积 |
| 维护成本 | 低（只需索引） | 中（LLM 自动维护） |
| 知识深度 | 浅层匹配 | 深层综合 |
| 用户参与 | 被动接收 | 主动策展+指导 |

### 配套工具

- [[Obsidian]]：最适合作为 Wiki IDE，带 Graph View、Dataview 插件、Marp 演示
- [[Obsidian Web Clipper]]：浏览器扩展，快速将网页转为 Markdown 投入原始素材层
- [[qmd]]：本地 Markdown 搜索引擎，支持混合 BM25/向量搜索和 MCP Server
- [[NotebookLM]]：Google 的 AI 研究助手，适合初步素材消化

### 为什么这个模式有效

维护知识库最繁琐的不是阅读或思考——而是"记账"：更新交叉引用、保持摘要最新、记录矛盾、维护数十页的一致性。人类会因维护负担放弃 Wiki，而 LLM 不会厌倦、不会忘记更新交叉引用，维护成本趋近于零。

人类的职责：策展来源、引导分析、提出好问题、思考意义。
LLM 的职责：其余一切。

这一理念在精神上可追溯至 Vannevar Bush 1945 年的 Memex 愿景——私人、精心策展、文档间关联路径与文档本身同等重要的知识存储。Bush 无法解决的问题是"谁来维护"，而 LLM 给出了答案。
